# Polish Bar — What "Successful" Means

A "successful repo janitor run" is not "the junk is gone." Every cleanup commit must satisfy these dimensions before the run can be declared complete.

---

## The 18 dimensions

| # | Dimension | Test | Phase |
|---|-----------|------|-------|
| 1 | **Recovery completeness** | Every candidate has a working-tree-copy in the bundle AND a meta entry AND an index row; byte-equality verified before any destructive phase | 3 |
| 2 | **Verdict evidence** | Every triage row cites concrete evidence (smell tag, ref-grep result, archetype rule, AGENTS.md mention); "looks like junk" alone is never acceptable | 4 |
| 3 | **No false-positive deletes** | No file is deleted when REFERENCE-GREP finds ≥1 inbound hit; any such candidate flips to `surface-to-user` | 4 |
| 4 | **No silently-broken references** | Every move's reference graph was checked; every reference either was rewritten (logged in `reference_rewrite_log.tsv`) or was surfaced to the user | 6 |
| 5 | **Per-commit gates** | Every Phase 6/7/8 commit has run the project's full test/typecheck/lint/build suite, and they all pass | 6, 7, 8 |
| 6 | **`.gitignore` shadowing audit** | Every newly-added `.gitignore` line was run through `git ls-files <glob>` to surface tracked-file shadowing before user sign-off | 5, 8 |
| 7 | **Focused commit messages** | Each commit explains *why* this change is happening; not "remove junk" but "remove 12 ephemeral SQLite WAL files generated by integration tests; add `*.db-wal` to `.gitignore`" | 6, 7, 8 |
| 8 | **Order of operations** | moves → deletes → `.gitignore` updates (in that sequence) | 6, 7, 8 |
| 9 | **Verbatim authorization** | Phases 7 and 8 only ran after the user typed the literal commands (or an authorization phrase that quotes them); recorded in `cleanup_authorization.txt` | 7, 8 |
| 10 | **Idempotent on a clean repo** | Re-running on a freshly-cleaned repo produces no commits and reports "nothing to do" | 1–10 |
| 11 | **Resumable** | If interrupted mid-Phase 6/7, re-running picks up from the last successful commit using `apply_log.tsv` + git log | 6, 7 |
| 12 | **Build still works** | After Phase 9, `<test_command> && <typecheck_command> && <lint_command> && <build_command>` succeeds from a clean checkout | 9 |
| 13 | **Phase 2.5 ran clean** | `secret_findings.tsv` is empty, OR every entry has a documented user resolution (rotation done, public-key-only, false-positive marked) | 2.5 |
| 14 | **Audit trail intact** | `apply_log.tsv`, `reference_rewrite_log.tsv`, `cleanup_authorization.txt`, and `handoff_report.md` all populated; backup ref + bundle still exist | 10 |
| 15 | **Verification log written** | If volatile-behavior operators ran (filter-repo, force-with-lease, LFS smudge), `verification_log.md` has corresponding entries (Axiom 17) | 1, harden-secret-leak |
| 16 | **Coverage matrix complete** | Every FILE-SMELLS rule has a row in `coverage_matrix.md`; no blank cells (Axiom 18) | 2.5 |
| 17 | **Phantom deletions handled** | If any phantom deletions were detected, they were resolved (restored or user-confirmed delete) before any cleanup commits landed (Axiom 24) | 1.5 |
| 18 | **Mode escalation recorded** | If a mode escalation occurred (e.g., triage-only → harden-secret-leak), `mode_escalation_decision.md` exists with user authorization (Axiom 21) | * |

## How `polish-bar-check.sh` enforces this

Run by the handoff-reporter at Phase 10:

```bash
bash scripts/polish-bar-check.sh <project>
```

Returns exit code 0 only if all 18 dimensions pass. Each failing dimension is logged to `.repo_janitor_workspace/polish_bar_failures.md` with diagnostic info.

Common failure patterns and fixes:

| Failure | Fix |
|---------|-----|
| Dimension 1: bundle missing a candidate | Re-run Phase 3 from the candidates.tsv |
| Dimension 4: a reference was missed | Phase 9 fresh-eyes catches this; re-run REFERENCE-GREP, do the rewrite via Edit tool, commit |
| Dimension 5: a per-commit gate failed | The skill should have halted; either the gate was skipped or the user pre-approved a known failure (recorded in `apply_log.tsv` with `gates_status=user-approved-known-fail`) |
| Dimension 6: a tracked file was shadowed | Either `git rm --cached` it (untrack) or narrow the glob; commit the fix |
| Dimension 7: a commit message says "remove junk" without per-file rationale | Use `git commit --amend` to rewrite the message before push |
| Dimension 8: order is reversed | Cherry-pick to reorder commits, OR explain in the handoff that the order doesn't matter for this case (rare; usually it does) |
| Dimension 12: build broken after Phase 9 | Roll forward — find the missed reference rewrite, fix it, re-run gates |
| Dimension 13: secret-finding unresolved | Switch to INCIDENT-PLAYBOOK; do not finalize the run until secret is rotated + history rewritten |
| Dimension 14: audit log gap | Reconstruct from git log + workspace artifacts; the run is technically incomplete until the log is repaired |

## "Done" vs "completed successfully"

The skill maintains a sharp distinction between these two states:

- **Done** = the user told the skill to stop, OR the skill hit a halt condition.
- **Completed successfully** = all 18 dimensions pass.

A run can be "done" without being "completed successfully" — for example:
- Phase 2.5 found a real secret; the user wants to rotate the key offline before continuing. The skill emits a partial handoff (Phases 1, 2, 2.5 complete; Phases 3–10 deferred) and stops.
- Phase 6 gates fail repeatedly on the same move; the user decides to skip that category. The skill records `category-skipped-by-user-decision` in the apply log and continues.
- Phase 5 user override changed >5 verdicts; the user said "I'll come back to this." The skill saves state and stops.

In all of these, the skill is "done" but not "completed successfully" — and that's fine. The handoff report explicitly says which dimensions did and didn't pass, so the user knows the state precisely.

## Polish-bar checks per phase

### Phase 1 (Reconnaissance)
- `project_profile.json` exists.
- `archetype` field is non-empty (or explicitly `unknown` with user confirmation).
- `protected_globs` is non-empty.
- `test_command`, `typecheck_command`, `lint_command`, `build_command` are all populated (empty strings allowed only if explicitly confirmed-no-such-gate by the user).

### Phase 2 (Inventory)
- `candidates.tsv` exists with at least the header row.
- `reference_graph.json` exists with one entry per candidate.
- `candidates_grouped.md` exists.
- Every candidate has at least one smell-tag.

### Phase 2.5 (Secret scan)
- `secret_findings.tsv` exists (may be empty).
- Every row in `secret_findings.tsv` has a `resolution` field set (one of: `halted-pending-rotation`, `rotated-then-rewritten`, `false-positive-confirmed`, `gitignore-only-per-user`, `keep-as-is-public-component`).

### Phase 3 (Bundle)
- `<bundle>/index.tsv` has one row per candidate from `candidates.tsv`.
- Every row's `path` exists at `<bundle>/working-tree-copies/<path>`.
- `bundle_verification.log` shows zero `MISMATCH` lines.
- `refs/repo-janitor-backup/<DATE>-pre-cleanup` exists.
- `<bundle>/README.md` exists.

### Phase 4 (Triage)
- Every candidate has exactly one row across all `batch_*.tsv` files.
- No row has empty `verdict` or `confidence`.
- No row has `verdict=delete*` AND `confidence<0.7` (forced to `surface-to-user`).
- No row has `verdict=delete*` AND `n_inbound_refs>0` (forced to `surface-to-user`).

### Phase 5 (Merge & Confirm)
- `triage.tsv` is the merged source of truth.
- `triage_decision.md` exists with categorized plan.
- `move_plan.md`, `delete_plan.md`, `gitignore_plan.md` exist.
- `user_overrides.tsv` reflects every user override (may be empty).
- User explicit "go" / "proceed" / "approved" recorded.

### Phase 6 (Apply moves)
- Every `move` row in `triage.tsv` has either `new_commit_sha` or `conflict-skipped` / `applied-by-other-agent` / `superseded-during-apply`.
- `reference_rewrite_log.tsv` has one row per rewrite.
- Every move-batch commit has gates recorded.

### Phase 7 (Apply deletes)
- Every `delete*` row in `triage.tsv` has `new_commit_sha` or a skip reason.
- `cleanup_authorization.txt` contains the verbatim user authorization text.
- Every delete commit has gates recorded.

### Phase 8 (Gitignore)
- One commit on the recovery branch with `.gitignore` changes.
- Shadowing audit captured in `gitignore_plan.md`.
- Verbatim authorization in `cleanup_authorization.txt` if any new pattern shadows tracked files.
- `git check-ignore -v <test-path>` confirms each new pattern fires.

### Phase 9 (Fresh-eyes)
- `fresh_eyes_log.md` shows ≥2 clean rounds (or ≥3 for Comprehensive variant).
- Final round runs every gate and they all pass.

### Phase 10 (Handoff)
- `handoff_report.md` exists with all sections populated.
- Beads issue filed (or `beads_skipped: true` recorded).
- Push commands printed for the user.
