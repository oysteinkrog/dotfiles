# AI Assist — Auto-Categorize, Suggested Replies, Dedup

The ticketing system can pull substantial leverage from selective LLM use. This file documents the high-ROI features, with cost models and failure modes.

## Feature Inventory

| Feature | ROI | Cost / ticket | Implementation cost | Risk |
|---|---|---|---|---|
| Auto-categorize on creation | High | ~$0.0002 | Low | Low |
| Suggested first response | High | ~$0.005 | Medium | Medium |
| Embedding-based dedup | High | ~$0.0001 | Low | Low |
| Sentiment / hostility flag | Medium | ~$0.0002 | Low | Low |
| Auto-tag by topic | Medium | ~$0.0002 | Low | Low |
| Customer-facing AI agent | Variable | ~$0.02-0.10 | High | High |
| Auto-summarize long threads | Medium | ~$0.005 | Low | Low |
| Reply quality auto-review | Medium | ~$0.003 | Low | Low |

**Use Claude API** (Sonnet for most; Haiku for cheap-and-fast classification; Opus for high-stakes):

```ts
import Anthropic from "@anthropic-ai/sdk";
const ai = new Anthropic({ apiKey: process.env.ANTHROPIC_API_KEY });
```

## Hard Rule: Never Auto-Send

The customer-facing reply path always has a human in the loop. AI drafts,
human reviews, human sends. Pre-approved templates can speed the review, but
they do not bypass the owner/support-agent confirmation gate.

## Hard Rule: Grounding Before Drafting

AI suggestions must carry their evidence with them. A draft is not ready for
admin review unless the system can show:

- ticket id and message ids used;
- KB/docs snippets used;
- policy/runbook section used;
- customer tier/SLA source, if referenced;
- model/provider/version;
- missing context warnings.

If a suggestion mentions a refund, legal/privacy rule, security claim, SLA, or
product behavior without a cited source, the UI should mark it "needs evidence"
instead of presenting it as send-ready.

## Hard Rule: Every AI-Drafted Reply Runs Through `/de-slopify`

Anything generated by an LLM in this file — suggested replies, summaries, AI-agent transcripts — **must** pass through `/de-slopify` before it touches a customer's inbox. Customers can spot LLM defaults (the "delve / robust / kindly / I'd be happy to help" cluster, the polished-but-soulless rhythm), and a single AI-tell shipped is harder to recover from than a slow reply.

Wire `/de-slopify` as the *last* step in the reply pipeline, after suggestion and after the agent's own edits:

```
[LLM suggest] → [agent edits] → [/de-slopify] → [send]
                                       ↑
                                       │
                              non-negotiable gate
```

If `/de-slopify` flags issues, the agent edits and re-runs. There is no "this reply is too short to bother slopifying" carve-out — the short ones leak slop just as visibly.

## Feature 1: Auto-Categorize On Creation

When a ticket is created, classify it into one of the `supportCategoryEnum` values. Helps:
- Routing (auth tickets to Alice, billing to Bob)
- Volume metrics (per-category)
- Auto-priority (security, data-loss → bump to P1)

```ts
// src/lib/ai/categorize.ts
const CATEGORIES = ["auth", "billing", "access", "bug", "content_moderation", "other"] as const;

export async function categorizeTicket(subject: string, body: string): Promise<typeof CATEGORIES[number]> {
  const r = await ai.messages.create({
    model: "claude-haiku-4-5-20251001",
    max_tokens: 50,
    messages: [{
      role: "user",
      content: `Classify this support ticket into ONE category: ${CATEGORIES.join(", ")}.

SUBJECT: ${subject}
BODY: ${body.slice(0, 2000)}

Reply with ONLY the category name. No explanation.`,
    }],
  });
  const text = (r.content[0] as any).text.trim().toLowerCase();
  return CATEGORIES.find(c => text.includes(c)) ?? "other";
}
```

Wire into ticket creation. This assumes `supportTickets` has a `category` column typed as `supportCategoryEnum` — if your base schema (per [SCHEMA.md](SCHEMA.md)) doesn't yet, add it as a nullable column first so existing rows aren't broken:

```ts
// schema addition
category: supportCategoryEnum(),  // nullable until backfilled
```

```ts
// /api/support/tickets POST
const ticket = (await db.transaction(async tx => {
  const t = await tx.insert(supportTickets).values({ ... }).returning();
  await tx.insert(supportMessages).values({ ticketId: t[0].id, ... });
  return t[0];
}));

// Async (non-blocking) categorize. `after()` is the Next.js helper that
// defers work until after the response is sent — keeps p95 low.
after(async () => {
  const category = await categorizeTicket(ticket.subject, ticket.description);
  await db.update(supportTickets)
    .set({ category })
    .where(eq(supportTickets.id, ticket.id));
});
```

Why `after()`: classification adds ~500ms. Don't block the user's submit on it.

## Feature 2: Suggested First Response

For routine categories (auth-reset, password-help, basic-billing), draft a first reply that the agent can edit-and-send.

```ts
// src/lib/ai/suggest-reply.ts
// Tier is NOT on the supportTickets row — it's derived from the user/org
// subscription (see SLA-ENGINE.md). Resolve it at the call site and pass it
// in so the prompt isn't built from `undefined`.
export async function suggestReply(
  ticket: Ticket,
  userTier: "free" | "individual" | "enterprise",
  voiceMd: string,
  kbContext: string
) {
  const r = await ai.messages.create({
    model: "claude-sonnet-4-6",
    max_tokens: 500,
    system: `You are drafting a support reply that matches this team's voice exactly.

VOICE GUIDE:
${voiceMd}

KB ARTICLES (citation-eligible):
${kbContext}

RULES:
- Match the register from the voice guide.
- Cite specific KB articles when relevant.
- Include at least one concrete specific (timestamp, error message, etc.) from the ticket.
- Sign off as the team's convention dictates.
- DO NOT use any banned phrases listed in the voice guide.`,
    messages: [{
      role: "user",
      content: `TICKET SUBJECT: ${ticket.subject}
TICKET BODY: ${ticket.description}
USER TIER: ${userTier}

Draft a reply.`,
    }],
  });
  return (r.content[0] as any).text;
}
```

In the admin UI, the suggestion appears as a "Draft" the agent can:
- Send as-is
- Edit and send
- Reject (provides feedback for future improvement)

**Track the rejection rate.** > 50% rejection = the suggestion isn't pulling weight; turn it off.

Store review outcomes:

| Outcome | Meaning |
|---|---|
| `accepted_as_is` | Rare; watch for over-trust. |
| `edited_lightly` | Useful suggestion. |
| `edited_heavily` | Helped with structure but not content. |
| `rejected_wrong` | Factual or policy error. |
| `rejected_voice` | Did not match the product's voice. |
| `rejected_missing_evidence` | Claimed more than it could prove. |
| `disabled_for_category` | Category is too risky or low value for AI assist. |

These outcomes feed the triage skill's post-send outcome loop. They should never
auto-patch policy or templates without owner review.

## Feature 3: Embedding-Based Dedup

When a new ticket is created, find existing open tickets with high similarity. Surface them to the agent.

```ts
// src/lib/ai/dedup.ts
export async function findSimilarOpenTickets(ticket: Ticket, threshold = 0.85) {
  const embedding = await embed(`${ticket.subject}\n${ticket.description}`);

  return await db.execute(sql`
    SELECT id, subject, status, created_at,
           1 - (embedding <=> ${embedding}::vector) AS similarity
    FROM support_tickets
    WHERE status IN ('open', 'acknowledged', 'in_progress', 'awaiting_customer')
      AND id <> ${ticket.id}
      AND created_at > now() - interval '30 days'
      AND 1 - (embedding <=> ${embedding}::vector) > ${threshold}
    ORDER BY similarity DESC
    LIMIT 5
  `);
}
```

Schema addition:

```ts
// in supportTickets:
embedding: vector("embedding", { dimensions: 1536 }),
```

After ticket insert, async-embed:

```ts
after(async () => {
  const embedding = await embed(`${ticket.subject}\n${ticket.description}`);
  await db.update(supportTickets)
    .set({ embedding })
    .where(eq(supportTickets.id, ticket.id));
});
```

In the admin UI, when an agent opens a ticket:

```tsx
{similarTickets.length > 0 && (
  <aside>
    <h3>Similar open tickets ({similarTickets.length})</h3>
    {similarTickets.map(t => (
      <a href={`/admin/support/tickets/${t.id}`}>
        {t.subject} ({Math.round(t.similarity * 100)}% match) — {t.status}
      </a>
    ))}
    <button onClick={() => mergeTickets(ticket.id, similarTickets[0].id)}>
      Merge into top match
    </button>
  </aside>
)}
```

Helps the agent see: "this is the same incident, 5 customers reported it" → escalate as outage rather than reply individually.

## Feature 4: Sentiment / Hostility Flag

Don't let a hostile escalation slip past Triage Phase 1.

The classifier should be a routing aid, not a replacement for the triage skill's [CUSTOMER-PSYCHOLOGY.md](../../user-support-triage-for-saas-and-open-source-projects/references/CUSTOMER-PSYCHOLOGY.md), [TACTICAL-EMPATHY.md](../../user-support-triage-for-saas-and-open-source-projects/references/TACTICAL-EMPATHY.md), or hostile-user runbook. It can say "this looks like stage 3 helplessness" or "legal-flavored"; it must not auto-send a de-escalation reply or auto-lock an account.

```ts
export async function flagSentiment(text: string): Promise<"normal" | "hostile" | "legal" | "security"> {
  const r = await ai.messages.create({
    model: "claude-haiku-4-5-20251001",
    max_tokens: 30,
    messages: [{
      role: "user",
      content: `Classify the tone/content of this support message into ONE of:
- normal
- hostile (insults, threats, doxxing, public shaming)
- legal (mentions lawsuit, regulator, lawyer, GDPR DSAR)
- security (mentions vulnerability, exploit, CVE)

MESSAGE:
${text.slice(0, 2000)}

Reply with only the label.`,
    }],
  });
  const t = (r.content[0] as any).text.trim().toLowerCase();
  return ["hostile", "legal", "security"].find(l => t.includes(l)) as any ?? "normal";
}
```

Hook into ticket creation. If non-normal:
- Set priority to P1 minimum
- Notify owner via Slack/email immediately
- Apply tier-3 lockdown procedures (see triage skill HOSTILE-USER runbook)

## Feature 5: Auto-Tag By Topic

Beyond enum categories, freeform topic tags help in analytics and search.

```ts
const r = await ai.messages.create({
  model: "claude-haiku-4-5-20251001",
  max_tokens: 100,
  messages: [{
    role: "user",
    content: `Extract 1-3 topic tags from this ticket. Tags should be specific (e.g., "stripe-webhook", "oauth-google", "csv-export"), not generic.

TICKET: ${subject}\n${body}

Reply with comma-separated tags only.`,
  }],
});
const tags = (r.content[0] as any).text.split(",").map(t => t.trim().toLowerCase()).slice(0, 3);
```

Stored in the ticket's `tags text[]` column. Aggregate weekly:

```sql
SELECT unnest(tags) AS tag, COUNT(*) AS ticket_count
FROM support_tickets
WHERE created_at > now() - interval '7 days'
GROUP BY tag
ORDER BY ticket_count DESC LIMIT 20;
```

Spikes here = product / docs gaps.

## Feature 6: Customer-Facing AI Agent (Use With Caution)

A "Pre-triage AI" that the user talks to before submitting. Risks: bad answers erode trust faster than a slow human.

Only enable if:
- KB is mature and well-maintained
- Owner reviews 100% of conversations for the first month
- Hard handoff path: "talk to a human" button, always visible
- Never used for: refund decisions, security questions, billing disputes, account suspensions, anything regulated

Pattern:

```ts
// /api/support/ai-chat
const r = await ai.messages.create({
  model: "claude-sonnet-4-6",
  max_tokens: 500,
  system: `You are a helpful first-line support assistant for ${PROJECT_NAME}.

KB ARTICLES (cite when relevant):
${kbContext}

RULES:
- Answer ONLY from the KB. If not in the KB, say "I'll route this to a human agent" and trigger handoff.
- NEVER make billing decisions or commitments.
- NEVER discuss security details.
- NEVER promise timelines.
- If user is hostile, switch to: "Let me get a human on this." and trigger handoff.

VOICE: ${voiceMd}`,
  messages: history,
});
```

When the AI defers, auto-create a ticket with full conversation transcript. The agent has full context.

Tracking:
- AI deflection rate (resolved without human)
- AI handoff rate (escalated)
- AI accuracy (audited replies later)

If accuracy drops below 95%, disable.

## Feature 7: Auto-Summarize Long Threads

A ticket with 15+ messages is hard to onboard onto. Generate a summary the agent reads first.

```ts
export async function summarizeThread(messages: SupportMessage[]) {
  const r = await ai.messages.create({
    model: "claude-haiku-4-5-20251001",
    max_tokens: 300,
    messages: [{
      role: "user",
      content: `Summarize this support thread for a new agent. Focus on: (1) what the user wants, (2) what we've tried, (3) where we got stuck, (4) what the user is asking for now.

THREAD:
${messages.map(m => `[${m.senderType}] ${m.message}`).join("\n\n")}

Be concise (max 5 sentences).`,
    }],
  });
  return (r.content[0] as any).text;
}
```

Display at the top of the admin ticket view when message count > 10.

## Feature 8: Reply Quality Auto-Review

Before an agent sends, run an auto-review for AI-tells (per VOICE-CALIBRATION.md from the triage skill).

```ts
export async function reviewReply(reply: string, voice: string): Promise<{ ok: boolean; issues: string[] }> {
  const r = await ai.messages.create({
    model: "claude-haiku-4-5-20251001",
    max_tokens: 200,
    messages: [{
      role: "user",
      content: `Review this support reply for AI-tells and voice mismatches.

VOICE GUIDE:
${voice}

REPLY:
${reply}

Return JSON: {"ok": boolean, "issues": ["..."]}.

Flag if it contains: "Unfortunately,", "I'd be happy to help", "kindly", "delve", em-dashes for emphasis, "robust", or any phrase listed as banned in the voice guide.`,
    }],
  });
  return JSON.parse((r.content[0] as any).text);
}
```

UI: a soft warning, not a block. Agent can override.

## Cost Model (Monthly)

For a project with 1000 tickets/month:

| Feature | Per-ticket cost | Monthly cost |
|---|---|---|
| Categorize + sentiment + tags | $0.0006 | $0.60 |
| Embedding (creation + KB) | $0.0001 | $0.10 |
| Suggested reply (avg 1.5 / ticket) | $0.0075 | $7.50 |
| Quality review | $0.003 | $3.00 |
| Auto-summarize (10% of tickets) | $0.0005 | $0.50 |
| **Total** |  | **~$12 / month** |

Rounding error vs the agent-time saved. Default: turn it all on except customer-facing AI agent.

## Failure Modes

| Failure | Why | Mitigation |
|---|---|---|
| AI generates a wrong refund commitment | Customer-facing AI given too much policy authority | Hard rule: human-in-loop for any commitment |
| AI mis-categorizes consistently | Out-of-distribution tickets | Track accuracy weekly; retrain prompt if drift |
| Suggested replies all sound the same | Voice guide too generic | Per-category voice samples; 5+ examples |
| Embedding-dedup matches dissimilar tickets | Threshold too low | Tune; 0.85 is a starting point |
| LLM API outage breaks ticket creation | Synchronous classification on path | Always async via background hook / queue / outbox (`after()` in Next.js) |
| AI-generated text ships without review | Auto-send enabled too aggressively | Default off; explicit per-category opt-in |
| Cost spike from unbounded auto-summarize | Trigger fires on every reply | Gate by message-count threshold |
