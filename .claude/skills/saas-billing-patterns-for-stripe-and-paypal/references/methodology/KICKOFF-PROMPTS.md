# Kickoff Prompts (per mode, verbatim)

Use these as the very first message you send to a fresh agent kicking off the skill in a particular mode. They're calibrated to set the right context, dispel common confusions, and produce the expected workspace artifact.

Pass `<placeholders>` substituted with actual values. Each prompt explicitly says where the workspace lives and what it should produce.

## `audit-only` kickoff

```
You are running the saas-billing-patterns-for-stripe-and-paypal skill in `audit-only` mode against the SaaS project at <PROJECT_PATH>.

Goal: produce a written audit. NO code changes. The user wants an honest assessment of how well the project's billing system implements the patterns in references/patterns/.

Workspace: <PROJECT_PATH>/.billing_workspace/

Required artifacts (in order):
1. .billing_workspace/phase0_mode.json   — record { mode: "audit-only", ... }
2. .billing_workspace/phase0_skill_inventory.json — from scripts/check-skills.sh
3. .billing_workspace/phase0_stack.json — from scripts/discover-stack.sh
4. .billing_workspace/phase1_archaeology_<bundle>.md per activated bundle from phase0_scope_decision.md — spawn one archaeologist per bundle in parallel; each follows the template in subagents/archaeologist.md
5. .billing_workspace/phase2_coverage_matrix.md — generated by scripts/generate-coverage-matrix.mjs then filled by coverage-mapper subagents per bundle
6. .billing_workspace/phase3_risk_scored_gaps.md — risk-scorer subagent
7. .billing_workspace/phase3_executive_summary.md — ≤2 pages for a non-engineer

FORBIDDEN in this mode:
- Edits to source code outside .billing_workspace/
- git commits on source files
- Provider API calls other than read-only catalog audits

Stop condition: phase3_executive_summary.md is committed and shown to the user. Recommend the next mode (typically audit-and-fix or harden-incident).

Read these references first:
- references/methodology/OPERATING-MODES.md (your mode's exit criteria)
- references/methodology/PHASES.md (the phase loop you follow)
- references/methodology/AGENT-PROMPTS.md (the subagent prompts you'll use)
- references/methodology/POLISH-BAR.md (the bar each pattern must clear to be marked `present`)
```

## `audit-and-fix` kickoff

```
You are running the saas-billing-patterns-for-stripe-and-paypal skill in `audit-and-fix` mode against the SaaS project at <PROJECT_PATH>.

Goal: audit the billing system, then close the gaps. Multi-PR program of work.

Workspace: <PROJECT_PATH>/.billing_workspace/
Branch: billing-hardening-<YYYYMMDD> (create at Phase 4 start)

Required artifacts (the full 10-phase loop):
1-3. As in audit-only mode (archaeology + coverage matrix + risk-scored gaps + executive summary).
4. .billing_workspace/phase4_implementation_plan.md — task graph respecting schema-before-code; create beads via `br create` if available.
5. Per-bundle implementation commits on the branch; same agent that did Phase 1 owns Phase 5 for its bundle.
6. .billing_workspace/phase6_harmonization_diff.md — cross-cutting consistency.
7. .billing_workspace/phase7_round_<N>_*.md per round; ≥2 consecutive clean rounds.
8. Real-DB integration tests under <project>/src/.../__tests__/; .billing_workspace/phase8_test_report.md.
9. .billing_workspace/phase9_drill_*.md per scenario.
10. <project>/docs/runbooks/ + .billing_workspace/phase10_secret_custody.md + .billing_workspace/phase10_oncall_doc.md.

CRITICAL discipline (RESPECT EXACTLY):
- Read AGENTS.md at <PROJECT_PATH> root before any code changes.
- NEVER delete a file without explicit user permission (AGENTS.md Rule #1).
- NEVER run a script that processes/changes code files (AGENTS.md "No Script-Based Changes").
- NEVER create _v2 / _improved / _enhanced files (AGENTS.md "No File Proliferation").
- NEVER `git reset --hard`, `git clean -fd`, `rm -rf` unless user explicitly authorizes.
- No backwards-compat shims; just fix the code.

Stop condition:
- All Phase 4 tasks closed
- Phase 7 fresh-eyes ran ≥2 consecutive rounds clean (only trivial edits)
- Phase 8 integration tests green; drift-guards in CI
- Phase 9 staging drills green
- Phase 10 runbooks committed; secret-custody matrix written
- The branch is up to date with origin (`git status` says "up to date")

Read these references first:
- references/methodology/OPERATING-MODES.md
- references/methodology/PHASES.md
- references/methodology/AGENT-PROMPTS.md (verbatim Phase 7 prompts)
- references/methodology/OPERATORS.md
- references/methodology/POLISH-BAR.md
- references/patterns/00-NORTH-STAR.md (load this into context before any other bundle)
- references/patterns/110-OPERATIONS.md (Battle-tested-checklist for ordering reference)

## `harden-incident` kickoff

```
You are running the saas-billing-patterns-for-stripe-and-paypal skill in `harden-incident` mode against the SaaS project at <PROJECT_PATH>.

A REAL production billing incident just happened. Goal: RCA-driven scoped fix first, then expand to audit-and-fix on the touched bundles.

Incident summary (from the user):
<INCIDENT_DESCRIPTION>

Workspace: <PROJECT_PATH>/.billing_workspace/

Required artifacts (incident-driven phase loop):
1. .billing_workspace/phase0_incident_brief.md — incident description, blast radius, suspected root cause, customer impact, monetary impact (so far).
2. .billing_workspace/phase1_archaeology_<incident_bundle>.md — scoped to incident blast radius.
3. .billing_workspace/phase4_rca_plan.md — RCA-driven fix plan; ordering: stop-the-bleed first, regression test second, broader hardening third.
4. Phase 5 scoped fix; commits on a branch named `incident-<short-name>-<YYYYMMDD>`.
5. Phase 7 fresh-eyes (mandatory; do NOT skip under time pressure — incident-pressure code is the most likely to introduce new bugs).
6. Phase 8 regression test that pins the EXACT incident reproduction case (named `bd-incident-<short-name>__<scenario>.test.ts`).
7. Phase 9 drill of the EXACT incident scenario in staging.
8. .billing_workspace/phase10_postmortem.md — formatted as: what happened, what we expected, root cause (5 whys), fix, regression test name, what we'll detect next time, who was paged when, customer impact, $$ impact.

After the postmortem lands: SWITCH TO `audit-and-fix` MODE on the touched bundles. The incident exposed one bug; there are likely sibling bugs in the same bundles.

Stop condition:
- Postmortem committed
- Incident's exact reproduction case is now a green test in CI
- Production-ready alarm wired for the failure mode (so next time it fires before customer support)
- User has acknowledged the postmortem
- Switched to audit-and-fix on touched bundles

Discipline: same as audit-and-fix mode. AGENTS.md rules apply. Do NOT amend the original incident commit; create new commits.

Read these references first:
- references/methodology/INCIDENT-RESPONSE-PLAYBOOK.md (the postmortem template + RCA framework)
- references/patterns/<incident_bundle>.md (the bundle covering the failure class)
- references/patterns/110-OPERATIONS.md § Failure-mode catalog (your incident likely matches one of the 38)
```

```
You are running the saas-billing-patterns-for-stripe-and-paypal skill in `migration` mode against the SaaS project at <PROJECT_PATH>.

Migration: from <CURRENT_BILLING_SYSTEM> to <TARGET_BILLING_SYSTEM>.

Goal: provider-symmetric refactor + cross-provider duplicate-sub guard + cutover with rollback path.

Workspace: <PROJECT_PATH>/.billing_workspace/
Branch: billing-migration-<short-name>-<YYYYMMDD>

Required artifacts (extra phase 9.5 cutover):
1. .billing_workspace/phase0_migration_brief.md — current system inventory, target system, what stays same, what must move.
2. .billing_workspace/phase1_archaeology_<bundle>.md per bundle (BOTH old and new providers).
3. .billing_workspace/phase4_provider_mapping.md — event → handler equivalences for old and new providers.
4. Per-bundle implementation; the canonical writer becomes provider-symmetric.
5. Phase 6 harmonization (especially for the cross-provider probe).
6. Phase 7 fresh-eyes (mandatory; cross-provider bugs are easy to introduce).
7. Phase 8 integration tests for both providers including cross-provider scenarios.
8. Phase 9 staging drills for both providers.
9. Phase 9.5 — CUTOVER PLAN (see references/methodology/MIGRATION-CUTOVER.md):
   - Dual-run window plan (≥2 weeks).
   - Canary subscription migration in staging.
   - Rollback path EXERCISED in staging.
   - Cutover runbook with explicit go/no-go gates.
10. Phase 10 runbooks + ops handoff.

CRITICAL discipline:
- Plan a real dual-run window, not a flag-flip cutover.
- Don't migrate paying customers automatically; let them migrate organically as their subs renew.
- Keep the old provider's webhook handler running until ALL old customers have migrated.
- Document the rollback path; exercise it in staging before approval to cut over.

Stop condition:
- Cutover dry-run successful in staging.
- Rollback tested.
- A live customer's first payment landed cleanly through the new provider.
- All old-provider state is reconciled or explicitly marked migrated.

Read these references first:
- references/methodology/MIGRATION-CUTOVER.md
- references/patterns/130-MIGRATION-CUTOVER.md (if extended bundle exists)
- references/patterns/00-NORTH-STAR.md

## How to use these prompts

1. The user invokes the skill with their goal.
2. You ask the Up-Front Confirmations (mode, providers, risk appetite, branch).
3. Once mode is confirmed, send the matching prompt to a fresh worker agent (or to yourself, in solo tier).
4. The worker reads the references named in the prompt, then begins Phase 0.

The prompts are intentionally LONG. They establish context that will be lost if Phase 1's first action is "let me start by reading the codebase." Front-loading the discipline is what makes the worker's first commits respect AGENTS.md instead of needing a Phase 7 round to clean up.
