# TypeScript Deep Dive — Per-Construct Harmonization for TS / JS

[LANGUAGE-PROFILES.md § TypeScript / JavaScript](LANGUAGE-PROFILES.md#typescript--javascript) covers the basic fingerprint patterns. This file goes deeper into TS/JS-specific harmonization decisions: dependency conflicts, type-system composition, JSX/component patterns, hook ordering, and build-config gotchas. It pairs with [RUST-DEEP-DIVE.md](RUST-DEEP-DIVE.md) — the same kind of deep dive for Rust.

> **Why a separate reference?** TypeScript has more *config-level* and *type-system-level* harmonization rules than most languages: tsconfig paths mappings, decorator order, generic type parameter constraints, JSX prop forwarding, hook call ordering, lockfile zoo (npm vs pnpm vs yarn vs bun). Each one has subtle composition semantics. A TS-aware harmonization-planner reading *this file* catches issues a generic synthesis would miss.

The skill activates this reference when `project_profile.json:archetypes` includes `npm-workspaces`, `pnpm-workspaces`, `turborepo`, `nx`, OR any branch fingerprint contains `*.ts` / `*.tsx` / `*.js` / `*.jsx` constructs. Comprehensive and Council modes spawn a `language-specialist-ts` subagent that reads this file in full.

## 1. `package.json` Conflicts

The TS/JS counterpart to Rust's `Cargo.toml`. Conflicts arise across `dependencies`, `devDependencies`, `peerDependencies`, `scripts`, `engines`, `workspaces`, etc.

### 1.1 Dependency additions are additive

```json
// branch A
"dependencies": { "lodash": "^4.17.21" }

// branch B
"dependencies": { "axios": "^1.6.0" }

// synthesis: union
"dependencies": { "axios": "^1.6.0", "lodash": "^4.17.21" }
```

Trivial union; the harmonization-planner sorts alphabetically (the `npm` / `pnpm` convention).

### 1.2 Version-range conflicts: prefer the highest semver

```json
// branch A
"dependencies": { "react": "^18.2.0" }

// branch B
"dependencies": { "react": "^18.3.1" }

// synthesis: pick the highest semver-compatible version
"dependencies": { "react": "^18.3.1" }
```

Tiebreaker: most-recent commit date.

If branches diverge on the *major* version (`^18.x` vs. `^19.x`), surface to user — major-version bumps require code changes elsewhere (React 18 → 19 has breaking changes; same for Next.js 14 → 15, etc.).

### 1.3 `scripts` conflicts

```json
// branch A
"scripts": { "build": "tsc && vite build" }

// branch B
"scripts": { "build": "next build" }

// surface to user — these encode different build pipelines
```

Surface to user. Build scripts are project-defining decisions; auto-merging produces a non-functional build.

```json
// branch A
"scripts": { "lint": "eslint ." }

// branch B (adding a new script, not overriding)
"scripts": { "lint": "eslint .", "format": "prettier --write ." }

// synthesis: union
"scripts": { "format": "prettier --write .", "lint": "eslint ." }
```

Additive when scripts are *new*; surface when scripts are *changed*.

### 1.4 `peerDependencies` and `peerDependenciesMeta`

```json
// branch A
"peerDependencies": { "react": "^18.0.0" }

// branch B
"peerDependencies": { "react": "^17.0.0 || ^18.0.0" }

// synthesis: B's broader range subsumes A's narrower range
"peerDependencies": { "react": "^17.0.0 || ^18.0.0" }
```

Pick the broader peer range; narrower ranges add no value when the broader works.

If the ranges are *disjoint* (`^16.0.0` vs `^18.0.0`), surface to user.

### 1.5 `workspaces` field (npm/yarn workspaces)

```json
// branch A
"workspaces": ["packages/*"]

// branch B
"workspaces": ["packages/*", "apps/*"]

// synthesis: union, dedup
"workspaces": ["apps/*", "packages/*"]
```

Always additive. Like Cargo workspace members; dropping a workspace pattern is high-risk.

## 2. Lockfile Conflicts

The TS/JS lockfile zoo:

- `package-lock.json` (npm, the default since npm 5)
- `yarn.lock` (Yarn 1.x and 2+)
- `pnpm-lock.yaml` (pnpm)
- `bun.lock` / `bun.lockb` (Bun; binary lockfile in older versions, text in newer)

All four are **regenerated post-merge** from `package.json`. Branches whose only diff is the lockfile classify as `garbage`.

```bash
# triage worker checks
diffs=$(git diff --name-only <merge-base>..<branch>)
case "$diffs" in
  "package-lock.json"|"yarn.lock"|"pnpm-lock.yaml"|"bun.lock"|"bun.lockb")
    verdict="garbage" ;;
esac
```

When a branch modifies `package.json` AND the lockfile, only `package.json` matters; the lockfile is regenerated by the install at Phase 8.

### 2.1 The "stale lockfile after harmonization" gotcha

After Phase 8 lands harmonized `package.json` changes:

```bash
# scripts/apply-keeper.sh fragment for harmonized synthesis on package.json
git add package.json
case "$PKG_MANAGER" in
  npm)  npm install --no-audit --no-fund ;;
  pnpm) pnpm install --frozen-lockfile=false ;;
  yarn) yarn install ;;
  bun)  bun install ;;
esac
git add "$LOCKFILE_NAME"     # adds the regenerated lock
git commit -m "..."
```

The skill never edits the lockfile by hand; it lets the package manager do it.

### 2.2 Multi-PM repos

Some monorepos accidentally have *both* `package-lock.json` and `pnpm-lock.yaml`. Surface to user; usually one is dead. The skill picks the most recently modified as the active one.

## 3. `tsconfig.json` Conflicts

`compilerOptions` is the main field.

### 3.1 Mostly additive

```json
// branch A
"compilerOptions": { "strict": true }

// branch B
"compilerOptions": { "skipLibCheck": true }

// synthesis: union
"compilerOptions": { "strict": true, "skipLibCheck": true }
```

### 3.2 Conflicting boolean options

```json
// branch A
"compilerOptions": { "noImplicitAny": true }

// branch B (canonical-aligned)
"compilerOptions": { "noImplicitAny": false }
```

Surface to user. Strict-mode flags are project-policy decisions; auto-resolving could either tighten or loosen the type discipline silently.

### 3.3 `paths` mappings need careful union

```json
// branch A
"paths": { "@/*": ["src/*"] }

// branch B
"paths": { "@components/*": ["src/components/*"] }

// synthesis: merge keys
"paths": {
  "@/*": ["src/*"],
  "@components/*": ["src/components/*"]
}
```

When two branches define the *same* alias key with different targets, surface to user — alias remapping is a non-trivial refactor signal.

### 3.4 `include` / `exclude` arrays

Additive union for `include`; intersection for `exclude` (broader exclusion is safer).

Watch for: a branch that adds `"node_modules"` to `exclude` when canonical doesn't have it (or vice versa). Surface; this can mask compile errors.

### 3.5 `extends` field (config inheritance)

```json
// branch A
"extends": "@tsconfig/strictest"

// branch B
"extends": "@tsconfig/node18"
```

Surface to user. Multiple `extends` (TS 5.0+) can layer them, but auto-composing is risky.

## 4. Type Definitions (`*.d.ts`)

### 4.1 Type definitions are usually additive

```typescript
// branch A: src/types/api.d.ts
export interface User { id: string; email: string; }

// branch B: src/types/api.d.ts
export interface Order { id: string; total: number; }

// synthesis: both interfaces (different names = no conflict)
export interface User { id: string; email: string; }
export interface Order { id: string; total: number; }
```

### 4.2 Conflicting interface declarations

When two branches declare the *same* interface with different fields:

```typescript
// branch A
export interface User { id: string; email: string; }

// branch B
export interface User { id: string; email: string; createdAt: Date; }
```

If branch B's interface is a *strict superset* of branch A's, adopt B's. If they diverge (different field types, different optional markers), surface to user.

### 4.3 Type augmentation via `declare module`

```typescript
// branch A
declare module 'next' {
  interface NextApiRequest {
    user?: { id: string };
  }
}

// branch B
declare module 'next' {
  interface NextApiRequest {
    requestId?: string;
  }
}

// synthesis: TS merges declare module augmentations automatically
declare module 'next' {
  interface NextApiRequest {
    user?: { id: string };
    requestId?: string;
  }
}
```

Module augmentations are additive at the language level. The synthesis preserves both.

## 5. Generic Type Parameter Conflicts

Generics have constraint complexity.

### 5.1 Compatible constraint additions

```typescript
// canonical
function process<T>(input: T): T { ... }

// branch A
function process<T extends { id: string }>(input: T): T { ... }
```

Adding a constraint where there was none narrows the function's domain. Surface to user — call sites that pass `T` without an `id` field will break.

### 5.2 Multiple branches add different constraints

```typescript
// branch A
function process<T extends { id: string }>(input: T): T

// branch B
function process<T extends { name: string }>(input: T): T
```

Surface to user. Combining as `T extends { id: string; name: string }` (intersection) may not be what either branch intended.

### 5.3 Generic parameter renaming

```typescript
// canonical
function map<T, U>(items: T[], fn: (t: T) => U): U[]

// branch
function map<TIn, TOut>(items: TIn[], fn: (t: TIn) => TOut): TOut[]
```

Cosmetic; treat as `naming` intent. Adopt canonical's convention.

## 6. Decorator Usage (Angular / NestJS)

Decorator order matters for runtime semantics.

```typescript
// branch A
@Injectable()
@Transactional()
class UserService { ... }

// branch B
@Transactional()
@Injectable()
class UserService { ... }
```

Different decoration order can change runtime behavior (e.g., transaction wrapping vs. DI registration). Surface the order to user; ask which is correct.

### 6.1 Adding decorators

```typescript
// branch A: adds @Logged
// branch B: adds @CacheResult

// synthesis: stack both, but ORDER MATTERS
@Logged()
@CacheResult()
async fetch(): Promise<Data> { ... }
```

The harmonization-planner picks an order based on intent: outer = applied last (runs first or last depending on decorator semantics; typically: outer wraps inner). Surface for user review.

## 7. `export` vs. `export default` Conflicts

```typescript
// branch A
export function Button() { ... }

// branch B
export default function Button() { ... }
```

This is a `divergent-refactor`. Default exports vs. named exports change the import syntax at every call site. Surface to user.

### 7.1 Ambient additions

When branch A adds `export default Button` and canonical already has `export function Button`, that adds a default export alongside the named export — usually safe (call sites can use either form). But it can cause confusion; surface for review.

## 8. JSX / TSX Component Conflicts

### 8.1 Children prop is usually additive

```tsx
// canonical
<Card title="..." />

// branch A
<Card title="..." footer={<Footer />} />

// branch B
<Card title="...">
  {someContent}
</Card>
```

If the underlying component supports both `footer` prop and `children`, both compose. The harmonization-planner adopts both forms.

### 8.2 Props additions are additive

```tsx
// branch A
interface ButtonProps { variant?: 'primary' | 'secondary'; }

// branch B
interface ButtonProps { size?: 'sm' | 'md' | 'lg'; }

// synthesis
interface ButtonProps {
  variant?: 'primary' | 'secondary';
  size?: 'sm' | 'md' | 'lg';
}
```

### 8.3 Ref forwarding is risky

```tsx
// canonical
function Button(props: ButtonProps) { ... }

// branch
const Button = forwardRef<HTMLButtonElement, ButtonProps>((props, ref) => { ... });
```

Adopting `forwardRef` is structural — call sites that previously didn't pass `ref` are unaffected, but the type signature changes. Surface to user.

### 8.4 Memoization additions

```tsx
// canonical
function ExpensiveComponent({ data }) { ... }

// branch
const ExpensiveComponent = React.memo(function ExpensiveComponent({ data }) { ... });
```

Pure perf optimization; usually safe to adopt. The harmonization-planner adopts memoization as a refactor; flags for user if the component uses unstable callback props (memo would be ineffective).

## 9. React Hooks

Order matters; rules-of-hooks must be preserved.

### 9.1 Hook order is part of the synthesis contract

```tsx
// branch A — adds useEffect
function Component() {
  const [state, setState] = useState(0);
  useEffect(() => { ... }, []);
  return <div>{state}</div>;
}

// branch B — adds useCallback
function Component() {
  const [state, setState] = useState(0);
  const cb = useCallback(() => setState(s => s + 1), []);
  return <button onClick={cb}>{state}</button>;
}

// synthesis: preserve hook order across variants
function Component() {
  const [state, setState] = useState(0);             // canonical
  const cb = useCallback(() => setState(s => s + 1), []);  // from B
  useEffect(() => { ... }, []);                       // from A
  return <button onClick={cb}>{state}</button>;
}
```

The synthesis must:

1. Preserve canonical's hooks first.
2. Add new hooks in the order they appear in their source variant.
3. Ensure the final order doesn't violate rules-of-hooks (no conditional calls).

### 9.2 Conditional hooks are forbidden

```tsx
// branch A — VIOLATES rules-of-hooks
function Component({ enabled }) {
  if (enabled) {
    const data = useFetch();   // ← hook in conditional!
  }
  return ...;
}
```

The harmonization-planner refuses to compose this pattern. Surface to user; the violation must be fixed by the user.

### 9.3 Effect deps array

```tsx
// branch A
useEffect(() => { fetch(id); }, [id]);

// branch B
useEffect(() => { fetch(id, ttl); }, [id, ttl]);
```

If both branches add the same effect with overlapping deps, the synthesis takes the union of deps:

```tsx
useEffect(() => { fetch(id, ttl); }, [id, ttl]);
```

Watch for: deps that one branch *removes* (incorrect). Surface to user.

## 10. Test Files

### 10.1 Test files are usually additive

```typescript
// branch A: tests/api/user.test.ts
describe('User', () => {
  it('renders correctly', () => { ... });
});

// branch B: tests/api/user.test.ts
describe('User', () => {
  it('handles errors', () => { ... });
});

// synthesis: both `it`s in the same describe
describe('User', () => {
  it('renders correctly', () => { ... });
  it('handles errors', () => { ... });
});
```

### 10.2 Test framework conflicts

Vitest vs. Jest vs. Mocha vs. Playwright. If two branches use different frameworks for the same logical test, surface to user.

### 10.3 Snapshot files (`__snapshots__/*.snap`)

Snapshots regenerate on test run. Branches that modify only snapshot files: `garbage` (regenerate post-merge).

```bash
# triage worker
diffs=$(git diff --name-only <merge-base>..<branch>)
echo "$diffs" | grep -qE '\.snap$|__snapshots__' && \
  ! echo "$diffs" | grep -qvE '\.snap$|__snapshots__' && \
  verdict="garbage"
```

`*.stories.tsx`, `*.mdx` files: usually additive.

```tsx
// branch A: src/Button/Button.stories.tsx
export const Primary: Story = { args: { variant: 'primary' } };

// branch B: src/Button/Button.stories.tsx
export const Disabled: Story = { args: { disabled: true } };

export const Primary: Story = { args: { variant: 'primary' } };
export const Disabled: Story = { args: { disabled: true } };
```

The story `default export` (the meta) usually doesn't conflict; if it does (different Title, different Component), surface to user.

## 12. Build Config Files

### 12.1 `vite.config.ts` / `next.config.ts` / `webpack.config.js`

Build configs are project-defining. Auto-merging is risky.

| Diff type | Action |
|---|---|
| New plugin added | Surface; ask user if the plugin should be in canonical |
| Existing plugin's options changed | Surface |
| Output directory change | Surface — affects deployment |
| Devtool / sourcemap setting change | Surface — affects DX |
| Alias additions (e.g., resolve.alias) | Additive; usually safe to compose |

Default: **surface most build-config changes to user**.

### 12.2 `next.config.ts` (Next.js)

Specific concerns:

- `redirects()` / `rewrites()` — additive arrays; merge.
- `experimental` flags — surface (experimental flags can break builds).
- `images.domains` / `images.remotePatterns` — additive; union.

### 12.3 ESLint / Prettier configs

`.eslintrc.json`, `.prettierrc`, `eslint.config.js`:

- Rule additions: additive; merge.
- Rule overrides: surface (overriding a rule is a policy decision).
- Plugin additions: additive; merge.
- `extends` array: surface (changes the inheritance chain).

## 13. Worked Example — `feature/auth-rework` Synthesis on `lib/auth.ts`

A concrete TS synthesis showing every rule applied at once. This is the canonical TS example for the harmonization plan.

### 13.1 Variant matrix (excerpt)

```

variant                            | hunks                                                    | intent       | conf
-----------------------------------|----------------------------------------------------------|--------------|-----
canonical                          | (baseline; getSession() at line 47)                      | base         | —
agent-cleanup-pass-3               | + null-token guard at top of getSession                  | defensive    | 0.92

feature/refresh-token-rotation     | + refresh token rotation logic                           | refactor     | 0.86

```

### 13.2 Composition decisions

Per [HARMONIZATION.md § 4](HARMONIZATION.md):

1. **Defensive checks compose** — null-token + JWT validation + zod schema all survive.
2. **Refactor + error-handling compose if compatible** — refresh rotation + typed AuthError compose, with rotation throwing typed errors.
3. **Type-narrowing via zod is additive** — the zod schema becomes the canonical input validator.
4. **Tests lift additively** — all fixtures from `feature/auth-test-fixtures` plus tests from individual variants.

### 13.3 Final synthesis (the actual TS code)

```typescript
// src/lib/auth.ts — harmonized synthesis from 6 branches.
//
// Recovered defensive checks from agent-cleanup-pass-3, feature/jwt-validation,
// feature/zod-input-validation. Adopted refactor from feature/refresh-token-rotation
// with error-handling composition from feature/typed-error-result. Test fixtures
// lifted from feature/auth-test-fixtures.

import { z } from 'zod';
import { jwtVerify } from 'jose';

// Discriminated union from feature/typed-error-result
export type AuthError =
  | { kind: 'null_token' }
  | { kind: 'invalid_jwt'; reason: string }
  | { kind: 'expired_token' }
  | { kind: 'shape_violation'; issues: z.ZodIssue[] }
  | { kind: 'rotation_failed'; cause: unknown };

export type AuthResult<T> = { ok: true; value: T } | { ok: false; error: AuthError };

// Zod schema from feature/zod-input-validation
const TokenSchema = z.object({
  access: z.string().min(1),
  refresh: z.string().min(1).optional(),
  expiresAt: z.number().int().positive(),
});

export type Token = z.infer<typeof TokenSchema>;

/**
 * Get the active session.
 *
 * Defensive guards (in entry order, cheapest first):
 *   1. Null-token check (from agent-cleanup-pass-3)
 *   2. Zod shape validation (from feature/zod-input-validation)
 *   3. JWT signature + expiry validation (from feature/jwt-validation)
 *
 * Refresh-token rotation logic (from feature/refresh-token-rotation) wraps
 * the body. All errors are typed via AuthError (from feature/typed-error-result).
 */
export async function getSession(
  token: unknown,
  jwks: import('jose').JWTVerifyGetKey
): Promise<AuthResult<Session>> {
  // Defensive layer

  if (token === null || token === undefined) {                       // from agent-cleanup-pass-3
    return { ok: false, error: { kind: 'null_token' } };
  }

  const parseResult = TokenSchema.safeParse(token);                  // from feature/zod-input-validation
  if (!parseResult.success) {
    return {
      ok: false,
      error: { kind: 'shape_violation', issues: parseResult.error.issues },
    };
  }
  const validated: Token = parseResult.data;

  // JWT validation                                                  // from feature/jwt-validation
  let claims;
  try {
    const { payload } = await jwtVerify(validated.access, jwks);
    claims = payload;
  } catch (err) {
    return {
      ok: false,
      error: { kind: 'invalid_jwt', reason: String(err) },
    };
  }

  if (typeof claims.exp !== 'number' || claims.exp * 1000 < Date.now()) {
    // Refresh-token rotation                                        // from feature/refresh-token-rotation
    if (validated.refresh) {
      try {
        const refreshed = await rotateRefreshToken(validated.refresh, jwks);
        return await getSession(refreshed, jwks);                    // recursive after rotation
      } catch (cause) {
        return { ok: false, error: { kind: 'rotation_failed', cause } };
      }
    }
    return { ok: false, error: { kind: 'expired_token' } };
  }

  return {
    ok: true,
    value: claimsToSession(claims),
  };
}

async function rotateRefreshToken(
  refresh: string,
  jwks: import('jose').JWTVerifyGetKey,
): Promise<unknown> {
  // Implementation from feature/refresh-token-rotation (preserved)
  // ...
  return { access: '...new...', refresh: '...new...', expiresAt: Date.now() + 3600_000 };
}

function claimsToSession(claims: import('jose').JWTPayload): Session {
  // Implementation from canonical (preserved)
  return { userId: claims.sub ?? '', exp: (claims.exp ?? 0) * 1000 };
}

export interface Session {
  userId: string;
  exp: number;
}
```

## 14. Cherry-Pick Gotchas Specific to TS / JS

### 14.1 Type-only imports breaking after refactor

```typescript
// canonical: import { User } from './types';
// branch (after refactor): import type { User } from './types';
```

Type-only imports are erased at compile time; runtime behavior is identical, but tooling (some bundlers, hot-reload) treats them differently. Cherry-pick may succeed; the per-apply `tsc --noEmit` gate catches type errors if any.

### 14.2 ESM vs. CJS module-format mismatch

If a branch was authored against ESM (`"type": "module"` in package.json) and canonical is CJS (or vice versa), import statements may not work. The per-apply gate's `tsc` and `node --check` catch most of these.

### 14.3 `const` enums and incremental compilation

`const enum Foo { Bar }` is inlined at compile time; if branches differ on whether an enum is `const`, the cherry-pick may succeed but consumers see different behavior. Surface to user.

### 14.4 React 18 → 19 strict-mode double-rendering

If a branch was authored against React 18 and the rationalization branch's gates run against React 19, double-rendering in dev mode may surface bugs in `useEffect` cleanup that weren't visible before. The per-apply test gate catches this; when caught, surface and fix.

## 15. Integration with TypeScript-Aware Linting

The skill runs the project's linters as part of every Phase 8 apply gate:

```bash
case "$LINTER" in
  eslint)        eslint --max-warnings=0 ;;
  biome)         biome check ;;
  oxlint)        oxlint ;;
esac
```

Findings on harmonized syntheses are surfaced explicitly:

| Linter class | Action |
|---|---|
| `react-hooks/rules-of-hooks` | Always block; rules-of-hooks violations are unsafe |
| `react-hooks/exhaustive-deps` | Surface; the harmonization may have introduced incorrect deps |
| `@typescript-eslint/no-explicit-any` | Cosmetic; ignore unless project config requires |
| `import/no-cycle` | Surface; circular dep may be the result of harmonized imports |
| `prefer-const` | Cosmetic; ignore |
