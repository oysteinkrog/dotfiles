# MESSAGE-BODY-SCHEMA-PER-TYPE.md — Mail Conventions for the 10 Subject Prefixes

<!-- TOC: Why per-type schemas | The 10 subject prefixes | KICKOFF schema | DELTA schema | COMPILED + CRITIQUE schemas | ACK + CLAIM + HANDOFF + BLOCKED + QUESTION + INFO | ACK semantics | DELTA role shorthand | Validation rules | Anti-patterns | Cross-references -->

Brennerbot uses Agent Mail (per AGENT-MAIL-CONVENTIONS.md) for inter-pane coordination. Without disciplined subject + body conventions, mail threads become unreadable; messages get lost; programmatic filtering breaks.

This file specifies the **10 subject prefixes**, the per-type body schema, the ACK semantics, and the role shorthand.

Mined from `/dp/brenner_bot/specs/message_body_schema_v0.1.md` and `thread_subject_conventions_v0.1.md`.

---

## Why per-type schemas

Three failures of free-form mail:

1. **No machine-readable structure** — orchestrators can't classify; manual triage required
2. **Inconsistent subjects** — operators can't scan inbox; programs can't filter
3. **No ACK discipline** — kickoffs go unacknowledged; sessions stall

Three benefits of per-type schemas:

1. **Subject-prefix routing** — orchestrator dispatches based on prefix
2. **Body validation** — each type has required fields; lint catches malformed
3. **ACK semantics per type** — kickoffs must be acked; deltas don't need it

## The 10 subject prefixes

| Prefix | Meaning | When to use | ACK required |
|--------|---------|-------------|---------------|
| `KICKOFF` | Session initiation | Starting a new research session or major work item | **Yes** |
| `DELTA[role]` | Agent contribution | Agent posting structured updates (role = model shorthand) | No |
| `COMPILED` | Merged artifact | Orchestrator posting compiled artifact | No |
| `CRITIQUE` | Adversarial feedback | Agent posting attack on current artifact | No |
| `ACK` | Acknowledgement | Confirming receipt of a message | (terminal) |
| `CLAIM` | Work claim | Agent claiming a bead or task | Yes |
| `HANDOFF` | Work handoff | Transferring work between agents | Yes |
| `BLOCKED` | Work blocked | Reporting a blocker on a task | No |
| `QUESTION` | Clarification request | Asking for input from agents or operator | Yes (response) |
| `INFO` | Informational | Status updates, announcements; non-actionable | No |

Format: `SUBJECT = {PREFIX}: {description}` (description ≤80 chars, human-readable)

## KICKOFF schema

**Purpose**: Initiate a new research session or major work item.

**Subject**: `KICKOFF: {description}`

**Body**:

```markdown
# {Session/Work Title}

## Research Question
{One-sentence problem statement; will become the RT}

## Context
{2-4 sentences of essential background}

## Excerpt
{Relevant transcript excerpt(s) with §n citations}

## MEMORY CONTEXT (cass-memory) (optional)
> **Provenance**: Generated by `cm context "<task>" --json` on {YYYY-MM-DD}.
> These are **heuristics**, not transcript evidence.

### Relevant rules (top 3-5)
- [{rule-id}] {one-line rule}

### Known pitfalls / anti-patterns (top 3-5)
- {one-line pitfall}

## Initial Hypotheses (optional)
{Seed hypotheses; will be refined by agents}

## Constraints (optional)
{Time bounds, scope limits, focus areas}

## Requested Outputs
{What artifacts/deliverables are expected}
```

**Validation**:

| Field | Required | Check |
|-------|----------|-------|
| Research Question | ✓ | non-empty H1 or `## Research Question` |
| Context | ✓ | `## Context` section present |
| Excerpt | recommended | `## Excerpt` with §n citations |
| Memory Context | optional | If present: clear provenance line; brief |

## DELTA schema

**Purpose**: Agent contribution to an artifact (per DELTA-PROTOCOL-FAIL-FAST.md).

**Subject**: `DELTA[role]: {description}`

**Body**:

```markdown
# Delta Contribution

{Optional prose explaining the contribution}

## Deltas

{One or more fenced ```delta blocks per delta_output_format_v0.1.md}
```

**Validation**:

| Field | Required | Check |
|-------|----------|-------|
| Delta blocks | ✓ | ≥1 ` ```delta ` block (per DELTA-PROTOCOL-FAIL-FAST.md fail-fast rule) |
| Valid JSON | ✓ | Each block parses |
| Operation | ✓ | ADD / EDIT / KILL |

**ACK Required**: No (deltas merged, not individually acked).

## COMPILED + CRITIQUE schemas

### COMPILED

**Purpose**: Orchestrator posting the compiled artifact after merging deltas.

**Subject**: `COMPILED: v{N} artifact`

**Body**:

```markdown
# Compiled Artifact v{N}

## Sources
- DELTAs from: {agent1, agent2, agent3}
- Round: {round_number}

## Artifact

{The full compiled artifact, OR a link to it}

## Lint Results
- Errors: {count}
- Warnings: {count}
- Info: {count}
```

**Validation**: artifact section present + lint summary.

### CRITIQUE

**Purpose**: Agent posting an attack on the current artifact (per TRIBUNAL-AND-OBJECTION-REGISTER.md).

**Subject**: `CRITIQUE: {target} (severity: {severity})`

**Body**:

```markdown
# Critique

## Target
{H-NNN | T-NNN | A-NNN | framing | methodology}

## Severity
{minor | moderate | serious | critical}

## Attack
{One paragraph: the specific argument}

## Evidence
{§n, EV-NNN, or [inference]}

## Suggested Resolution
{Optional: how to address}
```

## ACK + CLAIM + HANDOFF + BLOCKED + QUESTION + INFO schemas

### ACK

**Subject**: `ACK: {original-message-summary}`
**Body**: confirmation of receipt; ≤3 sentences.

### CLAIM

**Subject**: `CLAIM: {work-id}`
**Body**:

```markdown
# Claim
- Work ID: {bead_id or task description}
- Estimated wall-time: {estimate}
- Dependencies: {prerequisites}
```

### HANDOFF

**Subject**: `HANDOFF: {work-id} → {recipient}`
**Body**:

```markdown
# Handoff
- Work ID: {bead_id}
- From: {sender}
- To: {recipient}
- State so far: {summary}
- Next steps: {what recipient should do}
- Reason for handoff: {context loss, role mismatch, etc.}
```

### BLOCKED

**Subject**: `BLOCKED: {work-id} - {blocker-summary}`
**Body**:

```markdown
# Blocked
- Work ID: {bead_id}
- Blocker: {what's preventing progress}
- Required input: {what would unblock}
- Asked by: {sender}
- Asked of: {operator | other agent}
```

### QUESTION

**Subject**: `QUESTION: {topic}`
**Body**: question; required input; deadline if applicable.

### INFO

**Subject**: `INFO: {topic}`
**Body**: status update / announcement; non-actionable.

## ACK semantics

Acknowledgement is required when the sender needs to confirm the message was received and acted upon (or noted).

| Type | ACK required | When |
|------|--------------|------|
| KICKOFF | ✓ | All recipients must ack within timeout (per cockpit_runbook) |
| CLAIM | ✓ | Other agents ack to indicate "we know you're working on this" |
| HANDOFF | ✓ | Recipient acks to confirm acceptance of work |
| QUESTION | ✓ (response) | Asker waits for response; auto-ack on response |
| DELTA | ✗ | Merged deterministically; ack would be noise |
| COMPILED | ✗ | Information; not actionable |
| CRITIQUE | ✗ | Tracked via critique bead, not mail-ack |
| BLOCKED | ✗ | Information; resolution comes via response |
| INFO | ✗ | Non-actionable |

ACK timeouts (per cockpit_runbook): typically 5 min for KICKOFF, 10 min for HANDOFF, 30 min for QUESTION.

## DELTA role shorthand

The `[role]` in `DELTA[role]` is model-family shorthand:

| Shorthand | Model family | Program |
|-----------|--------------|---------|
| `opus` | claude-opus-* | claude-code |
| `gpt` | gpt-5.2 | codex-cli |
| `gemini` | gemini-3 | gemini-cli |
| `claude` | claude-sonnet/-haiku | claude-code (other models) |
| `human` | (operator) | (manual entry) |

Examples:

```
DELTA[opus]: Added H4 (epigenetic memory hypothesis)
DELTA[gpt]: Updated T1 potency check with viability assay
DELTA[gemini]: Added critique C3 re: dichotomy framing
DELTA[human]: Corrected §42 citation anchor
```

The role shorthand drives:
- Subject filtering (e.g., "show me all DELTA[gemini]")
- Per-model evaluation (per OPERATOR-CALIBRATION-LOG.md)
- Cross-session model A/B (per SESSION-REPLAY-AND-REPRODUCIBILITY.md)

## Validation rules

### Thread ID validation

| Check | Pattern | Error |
|-------|---------|-------|
| Engineering thread | `^[a-z0-9_-]+(?:\.[a-z0-9_-]+)*$` | `INVALID_BEAD_ID` |
| Research thread | `^RS-\d{8}-[a-z0-9-]{2,40}$` | `INVALID_RS_THREAD_ID` |
| Coordination thread | `^COORD-[a-z0-9-]{2,30}$` | `INVALID_COORD_THREAD_ID` |

### Subject validation

| Check | Pattern | Error |
|-------|---------|-------|
| Has valid prefix | `^(KICKOFF\|DELTA\[[a-z]+\]\|COMPILED\|CRITIQUE\|ACK\|CLAIM\|HANDOFF\|BLOCKED\|QUESTION\|INFO):` | `INVALID_SUBJECT_PREFIX` |
| Description ≤80 chars | `length(description) ≤ 80` | `SUBJECT_TOO_LONG` |
| DELTA role lowercase | `^DELTA\[[a-z]+\]:` | `INVALID_DELTA_ROLE` |

### Body validation

Per type (per the schemas above). Lint runs on every message at parse time; failures generate warnings or errors.

## Anti-patterns

| ✗ | Why |
|---|-----|
| Use ad-hoc subject like "Update on RS-..." | Doesn't match prefix pattern; breaks routing |
| KICKOFF without `## Research Question` | Validation fails |
| DELTA without ` ```delta ` fence | Per DELTA-PROTOCOL-FAIL-FAST.md: 0 blocks parsed |
| Skip ACK for KICKOFF | Per cockpit_runbook: KICKOFF without all-recipient ACK is stuck |
| Use COMPILED for individual deltas | COMPILED is the merged artifact; deltas use DELTA[role] |
| Mix multiple operations in DELTA[role] without clear structure | Lint may parse some but not all; rely on fence discipline |
| `DELTA[Opus]:` (capitalized) | Validator: lowercase per pattern |
| Subject longer than 80 chars | Description gets truncated in inbox views |
| Skip the threading (no thread_id correlation) | Mail thread becomes a flat list; can't reconstruct conversation |
| Use `INFO` for actionable items | Subscribers ignore INFO; use the right prefix |

## Composition with brennerbot phases

| Phase | Primary message types |
|-------|---------------------|
| 1 framing | KICKOFF (sets RT); QUESTION (clarifications) |
| 2 bootstrap | KICKOFF + ACK |
| 3 hypothesis | DELTA[role] (proposers); CRITIQUE (devil's-advocates) |
| 4 investigation | DELTA[role] (investigators); BLOCKED (when stuck) |
| 5 cross-exam | CRITIQUE (adversarial); CLAIM (taking adjudicator role) |
| 6 distillation | DELTA[role] (synthesizers); COMPILED (orchestrator) |
| 7 audit | CRITIQUE (auditors); QUESTION (clarification on findings) |
| 8 freeze | COMPILED (final); ACK (all roles confirm) |
| 9 handback | INFO (HANDBACK delivered) |
