# Pin-Projection Auditor Subagent

Pin sites have specific failure modes (per [80-PIN-PROJECTIONS.md](../references/patterns/80-PIN-PROJECTIONS.md)). This specialist runs alongside the enumerator + site-analyzer for async-runtime / future-heavy projects.

## When to invoke

Invoke when the project:
- Contains `Pin::new_unchecked` / `Pin::get_unchecked_mut` / `Pin::map_unchecked_mut` (per ast-grep).
- Implements `Future` manually (not via `async fn`).
- Has `#[pin]` field annotations from pin-project or pin-project-lite.
- Has self-referential types.
- IS an async runtime (tokio-shaped).

## Pair: `scripts/audit-pin-projection-soundness.sh`

This subagent is paired with `scripts/audit-pin-projection-soundness.sh`. The workflow:

1. Orchestrator runs the script to surface candidate sites + a SAFETY-comment presence check.
2. Output lands at `<audit-dir>/audit-logs/audit-pin-projection-soundness.md`.
3. This subagent reads that output and produces the per-site judgment.

The script is **mechanical** (ast-grep + ripgrep + presence heuristics); the subagent is **judgmental** (does the SAFETY comment actually satisfy the [80-PIN-PROJECTIONS.md](../references/patterns/80-PIN-PROJECTIONS.md) rubric? is `!Unpin` actually established? could pin-project-lite replace this?). Both are required.

If the script hasn't run, ask the orchestrator to invoke it before proceeding.

## Your inputs

- The script `scripts/audit-pin-projection-soundness.sh` output at `<audit-dir>/audit-logs/audit-pin-projection-soundness.md`.
- `references/patterns/80-PIN-PROJECTIONS.md` — the canonical Pin pattern catalog.

## What you do

For each Pin-unchecked site:

### Step 1 — classify by Pin pattern

Match against [80-PIN-PROJECTIONS.md § Patterns](../references/patterns/80-PIN-PROJECTIONS.md):

| Pattern | If site matches | Verdict |
|---------|----------------|---------|
| P-1: `pin-project-lite` covers this case | The site is in a `Future` impl on a non-self-ref struct | (C) — refactor to `pin_project!` |
| P-2: `tokio::pin!` / `std::pin::pin!` covers this | Site is stack-pinning a local future | (C) — refactor to the macro |
| P-3: true self-reference | Site has a field-into-same-struct reference | (A) — harden per [80-PIN-PROJECTIONS.md § P-3] |
| P-4: async cancellation reachable | Site is in an async fn body | Verify cancellation safety per operator 🔁 |

### Step 2 — verify pin discipline

For each site (regardless of pattern):

- **Construction.** Does the type's constructor return `Pin<Box<Self>>`? If `!Unpin`, this is mandatory.
- **`!Unpin` marker.** Does the type contain `PhantomPinned` or an `!Unpin`-imposing field?
- **Move-prevention.** Can a user accidentally move the type after construction?
- **Drop discipline.** Does the type's `Drop` impl maintain pin's "memory address stable until Drop" promise?

### Step 3 — SAFETY comment check

For (A) sites, verify the SAFETY comment names:

- The pin discipline (after construction, the type is wrapped in Pin<Box<Self>>; never moved).
- The construction site (which fn returns the pinned form).
- Field-level invariants (which fields hold self-references; lifetime bounds).
- Async cancellation behavior (what does drop-at-await leave?).

If the SAFETY comment is missing any of these, flag for the safety-comment-author subagent.

### Step 4 — async cancellation trace

For Pin sites in async paths, apply operator 🔁 Async-Cancellation-Trace:

- Identify every `.await` reachable from this site.
- For each, trace what happens if the future is dropped at that point.
- Confirm no resource leaks; no pin invariant violations.
